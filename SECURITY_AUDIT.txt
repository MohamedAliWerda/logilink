PART 1 - 2FA IMPLEMENTATION (CHANGES SHIPPED IN THIS SESSION)
================================================================================

GOAL
----
Add JWT 2-step authentication. When a user (student / admin / company) tries
to log in, send a 6-digit random verification code to their email and route
them to the existing /verify page. Only after entering the correct code does
the backend issue the JWT.

FLOW
----
  1) User submits credentials on /login-etudiant or /entreprise/loginen.
  2) Backend validates credentials BUT DOES NOT issue a JWT yet. Instead:
       - generates a cryptographically random 6-digit code
         (crypto.randomInt(0, 1_000_000), zero-padded)
       - stores a challenge in memory (Map): { challengeId UUID, code,
         account, attempts, expiresAt, lastSentAt }
       - emails the code to the user (Gmail SMTP, nodemailer)
       - responds with { challengeId, maskedEmail, type } - NO TOKEN.
  3) Frontend navigates to /verify, carrying challengeId/email/type in
     router state (history.state).
  4) User types the 6 digits and submits. Backend validates the code,
     consumes the challenge (single-use), and ONLY THEN returns:
       { access_token, user / entreprise, role }
  5) Frontend stores token + user/entreprise + role in localStorage and
     routes to the role-appropriate landing page:
       - admin     -> /admin/dashboard
       - etudiant  -> /home/dashboard or /home/cv-landing
       - entreprise-> /entreprise/offres

CHALLENGE LIFECYCLE
-------------------
  - TTL                : 10 minutes (CODE_TTL_MS)
  - Resend cooldown    : 60 seconds (RESEND_COOLDOWN_MS)
  - Max wrong attempts : 5 (MAX_ATTEMPTS), then challenge is destroyed
  - Code is destroyed on successful verification (consume() deletes it)
  - Expired challenges purged on every createChallenge / consume / resend

FILES ADDED
-----------
  backend/src/auth/two-factor.service.ts
      In-memory challenge store + SMTP sender with a styled HTML email
      template.

  backend/src/auth/dto/verify-2fa.dto.ts

  backend/src/auth/dto/signin-entreprise.dto.ts
      SignInEntrepriseDto   : { email: IsEmail, mot_de_passe: string }

NOTES / TRADE-OFFS
------------------
  - Challenge store is process-memory. Restarting the backend invalidates
    all pending codes. Multi-instance deployments would need Redis.
  - challengeId is the only "session" handle between step 1 and step 2;
    it is a random UUID v4, single-use, server-side bound to the
    authenticated identity. A leaked challengeId by itself is useless
    without the emailed code.
  - The masked email returned to the frontend exposes only the domain +
    first 1-2 chars of the local-part.
  - Reused the existing SMTP credentials (SMTP_USER / SMTP_PASS in
    backend/.env) - no new env vars required.


PART 2 - SECURITY AUDIT OF THE EXISTING PLATFORM
================================================================================

  Severity legend:  [CRIT] critical | [HIGH] high | [MED] medium | [LOW] low |
                    [INFO] informational

--------------------------------------------------------------------------------
 2.1 SECRETS / KEY MANAGEMENT
--------------------------------------------------------------------------------

[CRIT]  Supabase SERVICE-ROLE key shipped in the Angular bundle
        File: src/environments/environment.ts
        Key : `supabaseServiceRoleKey: 'eyJhbGciOi...'`
              `supabaseAnonKey: 'sb_publishable_...'`
        Impact: ANYONE who loads the SPA (or just opens the bundle in
                DevTools) has full-table read/write/delete on every
                Supabase table that does not have RLS enforced. With the
                service role JWT, RLS itself is bypassed. This is the
                single biggest issue in the platform.
        Used at: src/app/services/supabase.service.ts:14
                 (`this.supabaseAdmin = createClient(url, serviceRoleKey)`)
                 -> .adminClient is used by feedback_admin,
                 gestion_entreprise, score_admin, dashboard_admin,
                 register-entreprise, etc. (5+ components import it).
        Fix:    Remove the service-role key from the frontend entirely.
                Rotate the key in Supabase. Move every adminClient call
                behind a NestJS controller protected by JwtAuthGuard +
                role check. Keep only the publishable anon key on the
                client, and enforce RLS on every table.

[CRIT]  Plaintext passwords in DB (companies)
        File: src/app/services/supabase.service.ts:78
              .from('Societe').select('*')
                              .eq('email', email)
                              .eq('mot_de_passe', motDePasse)
        File: src/app/services/supabase.service.ts:363
              row.mot_de_passe = payload.password   (insert at registration)
        Impact: Society passwords are stored AND queried as plaintext.
                The login flow even compares password equality via SQL.
                Combined with the leaked service-role key, an attacker
                can SELECT * FROM "Societe" and harvest every password.
        Fix:    Hash with bcrypt on registration (the backend already
                imports bcrypt in auth.service.ts); never compare in SQL.
                The new POST /auth/signin-entreprise added in this audit
                does the bcrypt comparison server-side, but the stored
                rows are still plaintext until you re-hash existing data.

[HIGH]  Weak JWT secret default value
        File: backend/.env:4
              `JWT_SECRET=replace_with_a_strong_secret`
        Impact: If deployed with this default, tokens can be forged.
        Fix:    Replace with a 256-bit random value. Add a startup check
                that refuses to boot if JWT_SECRET equals this placeholder.

[HIGH]  SMTP password committed to .env in repo
        File: backend/.env:35-37
              `SMTP_USER=logilink.djagora@gmail.com`
              `SMTP_PASS=porquoaabshfhytu`
        Impact: Anyone with repo access can send mail as the platform.
                Useful for phishing students or companies.
        Fix:    .env should never be committed. Add it to .gitignore,
                rotate the Gmail app password, and store secrets in a
                proper secret manager (or at least environment variables
                set out-of-band).

[HIGH]  GEMINI / Hugging Face / MongoDB credentials in .env in repo
        File: backend/.env:7,11,21,24,28
        Impact: Same as above - third-party API tokens and a Mongo
                Atlas connection string are exposed to anyone with repo
                access (or who fetches the dotfile in production).
        Fix:    Rotate all keys, scrub from git history (BFG /
                git filter-repo), move to secret manager.

 2.2 AUTHENTICATION & SESSION
--------------------------------------------------------------------------------

[HIGH]  Token + sensitive user object stored in localStorage
        File: src/app/auth/verify/verify.ts:122-138
        Files: 17 components read/write to localStorage (token, user,
               entreprise, role).
        Impact: XSS (see 2.5) yields immediate, persistent token theft.
                Tokens are valid 7 days (auth.module.ts: expiresIn '7d').
        Fix:    Prefer httpOnly + Secure + SameSite=Strict cookies issued
                by the backend; or at least sessionStorage and a shorter
                expiry (<= 1h) plus refresh tokens.

[HIGH]  Role decided by client - role stored in localStorage
        File: src/app/auth/verify/verify.ts (stores `role` from JWT
              response payload, but front-end pages then *trust* the
              stored value).
        Impact: A user can edit localStorage.role to 'admin' and the
                Angular router will load the admin module without a
                guard (see next finding). Backend endpoints would still
                gate via JWT, but only those that USE JwtAuthGuard.
        Fix:    Never trust client-side role. Always validate on the
                server. Add an Angular RoleGuard that decodes the JWT
                and checks role claim before activating /admin/*.

[HIGH]  /admin/* routes have NO Angular guard at all
        File: src/app/app.routes.ts:56-99
              The 'admin' route tree is mounted without any canActivate.
        Impact: Any visitor can navigate to /admin/dashboard. The page
                will render (data calls will fail without a token, but
                the UI is exposed; sensitive labels, layouts, and lazy
                loaded modules become fingerprintable).
        Fix:    Add authGuard + roleGuard('admin') on the parent
                'admin' route.

[HIGH]  /entreprise/* routes have NO Angular guard
        File: src/app/app.routes.ts:106-121
        Same impact + fix as above (role 'entreprise').

[MED]   JWT strategy declares role union 'admin'|'etudiant' only
        File: backend/src/auth/strategies/jwt.strategy.ts:6-10
        Impact: The new entreprise JWT (role='entreprise') is issued by
                the AuthService but not typed in JwtPayload. Anything
                that reads `req.user.role` and narrows on the union may
                misclassify entreprise tokens. Cosmetic today, real
                hazard if role checks are added later.
        Fix:    Extend the union to include 'entreprise'.

[MED]   Password reset flow has a stub verify-code component
        File: src/app/auth/forgot-pass/verify-code.component.ts:21
              onSubmit() simply navigates to /reset-password without
              calling any backend.
        Impact: Anyone who reaches /verify-code can move to the
                password-reset screen. If reset is also client-side
                via supabaseAdmin (which it is - see 2.1), account
                takeover is trivial.
        Fix:    Wire forgot-password to a backend endpoint that issues
                a short-lived single-use token by email, and validate
                it server-side before allowing password change.

[LOW]   No account-lockout / rate-limit on /auth/signin
        Impact: Brute force on a known CIN is possible (no captcha,
                no IP throttle, no failed-attempt counter on the row).
        Fix:    Add @nestjs/throttler globally, and per-account
                lockout after N failures.

 2.3 AUTHORIZATION (BROKEN-OBJECT-LEVEL-ACCESS)
--------------------------------------------------------------------------------

[CRIT]  Company endpoints accept a societeId param with NO ownership check
        File: backend/src/offres/offres.controller.ts:33-50
              GET  /offres/company/:societeId
              GET  /offres/company/:societeId/candidatures
              GET  /offres/company/:societeId/candidatures/:studentId/cv
              POST /offres/create               (no guard at all)
              POST /offres/apply                (no guard at all)
              PUT  /offres/:id  + DELETE /offres/:id
        Impact: Classic IDOR. With a valid (or no) JWT, an attacker can
                substitute any company id and read all candidatures and
                CVs of competitors. They can also create offers under
                another company, edit/delete arbitrary offers, and
                apply for any student.
        Fix:    Add @UseGuards(JwtAuthGuard) on the whole controller.
                Compare the societeId in the URL against the JWT's
                societe id claim. Reject mismatches. Add similar checks
                on studentId in /apply (must equal req.user.sub).

[HIGH]  Admin endpoints in /admin/* (ancien-etudiants, dashboard, gaps)
        have NO JwtAuthGuard and NO role check
        File: backend/src/admin/ancien-etudiants.controller.ts (no guard)
              GET  /admin/ancien-etudiants    (returns all alumni emails)
              POST /admin/ancien-etudiants    (insert)
              POST /admin/ancien-etudiants/send-invitations (mass email!)
              POST /admin/ancien-etudiants/google-form-submission
              POST /admin/societe/send-approval-email
              POST /admin/societe/send-rejection-email
              POST /admin/societe/send-pending-email
        Impact: Unauthenticated callers can:
                - Dump alumni PII (name, email, promo, etc.)
                - Trigger Gmail-sender abuse: /send-invitations spams
                  every "Non contacté" alumni, /send-approval-email
                  sends mail to any email of the attacker's choosing
                  with an official "approved" message.
                - Insert arbitrary rows into ancien_etudiant /
                  feedback (mass-assignment - see 2.4).
        Fix:    @UseGuards(JwtAuthGuard) + role='admin' on the whole
                AdminModule. Validate `to` against the actual record's
                stored email on the approval/rejection endpoints.

[HIGH]  cv_submission, profile, recommendations endpoints trust
        whatever `auth_id` the JWT carries
        File: backend/src/cv_submission/cv-submission.controller.ts:55-85
              resolveAuthId() falls back to looking up user.auth_id by
              numeric id. Because the JWT 'sub' is filled from
              user.auth_id ?? String(user.id), a forged or wrong token
              with a malformed sub may still resolve to a real auth_id.
        Impact: With a leaked or weak JWT (see 2.2), a student could
                read another student's CV, ATS score, employability,
                and matching analyses by changing their sub claim.
        Fix:    JWT secret must be strong; never accept a sub that is
                not a UUID; do not "rehydrate" auth_id from a numeric
                id; map to the canonical UUID at login time and stick
                to it.

[MED]   /admin/recommendations is correctly guarded
        File: backend/src/recommendations/recommendations.controller.ts:17-19
              Has @UseGuards(JwtAuthGuard) + the controller resolves an
              adminAuthId from the JWT. Good pattern - apply elsewhere.

 2.4 INPUT VALIDATION & MASS-ASSIGNMENT
--------------------------------------------------------------------------------

[HIGH]  Many controllers accept `Body() body: Record<string, unknown>`
        without a DTO
        Files:
          backend/src/admin/ancien-etudiants.controller.ts (POST handlers)
          backend/src/offres/offres.controller.ts:67,72,82
          backend/src/cv_submission/cv-submission.controller.ts (any body)
        Impact: With `whitelist:true, forbidNonWhitelisted:true` in
                main.ts ValidationPipe, untyped bodies still flow
                through because no class is provided. Mass-assignment
                of unexpected DB columns is possible (e.g. setting
                'RÉPONSE'='A répondu' to game alumni stats; passing
                an arbitrary 'role' field into a future user insert).
        Fix:    Define class-validator DTOs for every @Body().

[MED]   String coercion of unknown payload fields opens injection in
        nested string operations
        File: backend/src/admin/ancien-etudiants.service.ts:67-114
              All values are passed straight to Supabase inserts after a
              `.trim()`. No length limit, no charset constraints.
        Impact: Stored XSS source if any of these fields are later
                rendered with [innerHTML] without sanitization; very
                large messages also become a DoS vector.
        Fix:    Validate length + character class on each field; encode
                on render.

[MED]   Stored XSS surface via [innerHTML] / bypassSecurityTrustHtml
        Files:
          src/app/user/home/component/dashboard/dashboard.html:21
            <div class="stat-icon" [innerHTML]="stat.icon"></div>
          src/app/user/home/component/dashboard/dashboard.ts:76-79
            sanitizer.bypassSecurityTrustHtml(icons[...])
          src/app/user/home/component/profil/profil.ts:644,729
            container.innerHTML = ... template literal containing
            bodyHtml that is built from user data.
        Impact: Right now `icons[]` is a hard-coded constant array, so
                no live exploit. The pattern is fragile though: any
                future change that feeds user content into one of those
                paths becomes a stored-XSS gate that bypasses Angular's
                sanitizer.
        Fix:    Avoid bypassSecurityTrustHtml for anything that *might*
                ever contain user input. Render icons as proper
                Angular components (<svg> in template) instead of
                strings + innerHTML.

[LOW]   Recursive table-name fallback on insert
        File: src/app/services/supabase.service.ts:372 (createSociete)
              Tries 'Societe' then 'societe'.
        Impact: Defensive but error-prone; combined with the next id
                being read from `select id order by id desc limit 1`
                this races (two parallel registrations can pick the
                same id). Not strictly a security issue, but it can
                cause integrity errors.
        Fix:    Let the DB own the primary key (identity / sequence).

 2.5 INFRASTRUCTURE / TRANSPORT
--------------------------------------------------------------------------------

[HIGH]  CORS configured as wide open
        File: backend/src/main.ts:20-23
              app.enableCors({ origin: true, credentials: true })
        Impact: `origin:true` reflects any origin and `credentials:true`
                sends cookies cross-site. Combined with localStorage
                tokens (sent via Authorization header rather than
                cookies), CSRF risk is lower TODAY, but any future
                move to cookie sessions opens a CSRF hole; right now
                it still allows any malicious site to make
                authenticated calls if they capture the token via XSS.
        Fix:    Hard-code the allowed origins (your Angular dev URL
                + prod domain) and only set credentials:true if you
                actually use cookies.

[MED]   `http://localhost:3001` hardcoded as API base in the bundle
        File: src/app/auth/services/auth-api.service.ts:40
              and 5+ other services.
        Impact: Production deploys silently break or hit the wrong
                host. Not a confidentiality issue but causes auth
                fragility.
        Fix:    Use environment.apiUrl everywhere.

[LOW]   No HSTS / CSP / X-Frame-Options headers from NestJS
        Impact: The app accepts being framed, sniffed, etc.
        Fix:    Add helmet (`npm i helmet`) and a strict CSP.

 2.9 RECOMMENDED IMMEDIATE ACTIONS (PRIORITISED)
--------------------------------------------------------------------------------

  1. Rotate the Supabase service-role key, the SMTP password, and every
     other key that ever lived in backend/.env or environment.ts.
     git filter-repo to scrub them from history.
  2. Remove `supabaseServiceRoleKey` from environment.ts. Move all
     admin-only data access behind NestJS endpoints with JwtAuthGuard
     + role check.
  3. Replace plaintext password storage on Societe with bcrypt; re-hash
     existing rows (force a password reset on next login).
  4. Add @UseGuards(JwtAuthGuard) + role check on AdminModule,
     OffresModule, and any other controller currently unguarded.
  5. Add Angular guards on /admin/* and /entreprise/* routes that decode
     the JWT (not the localStorage role string).
  6. Replace `origin: true` CORS with an explicit allow-list.
  7. Generate a real JWT_SECRET (256 bits) and add a startup assertion
     that refuses the placeholder value.
  8. Add @nestjs/throttler for /auth/* endpoints; add per-account lockout
     on failed 2FA attempts and failed login attempts.
